# 🎯 Главная идея

Секреты можно находить через комбинацию 4 подходов:

1. **Pattern-based detection (сигнатуры)**
    
2. **Context-based detection (контекст использования)**
    
3. **Entropy-based detection (математический анализ)**
    
4. **Structural validation (проверка структуры токена)**
    

Лучший результат даёт именно их комбинация.

---

# 1️⃣ Pattern-based detection (сигнатурный метод)

### Идея:

У большинства секретов есть предсказуемый формат.

Например:

- AWS ключи начинаются с `AKIA`
    
- GitHub токены с `ghp_`
    
- JWT всегда имеют 3 части через точку
    
- Приватные ключи имеют `-----BEGIN`
    

### Почему это работает:

Поставщики сервисов стандартизируют формат ключей.
### Минус:

Не находит кастомные токены.

---

# 2️⃣ Context-based detection (контекст)

Очень важный слой.

### Идея:

Даже если строка выглядит случайной — она подозрительна, если стоит рядом с ключевыми словами:

```
password =
api_key =
secret =
token =
client_secret =
```

То есть алгоритм:

1. Находим подозрительную строку
    
2. Проверяем 1–2 строки вокруг
    
3. Если есть контекстные слова → повышаем вероятность
    

---

# 3️⃣ Entropy-based detection (математика)

### Почему это круто:

Секреты выглядят как случайный шум.

Обычный текст:

```
database_password
```

Низкая энтропия.

Секрет:

```
kJH78sdKJH9823kjsdKJHsdkj23==
```

Высокая энтропия.

---

### Идея:

1. Берём строки длиной > 20
    
2. Считаем Shannon entropy
    
3. Если entropy > 4.5 → вероятный секрет
    

---

### Почему именно entropy:

Она измеряет "случайность" строки.

Чем равномернее распределены символы → тем выше энтропия.

---

# 4️⃣ Structural validation (проверка структуры)

Это то, что делает инструмент “умным”.

Примеры:

### JWT

- 3 части через `.`
    
- Base64
    
- Декодируется JSON
    
### AWS ключ

- длина 20
    
- только заглавные + цифры
    
### RSA ключ

- есть BEGIN и END

Если структура валидна → повышаем confidence.

---

# 🧠 Как объединить всё это

Можно сделать scoring систему.

Пример:

|Критерий|Баллы|
|---|---|
|Regex совпадение|+5|
|Высокая entropy|+3|
|Найден в .env|+2|
|Есть ключевые слова рядом|+2|
|Валидная структура|+3|

И дальше:

- 8+ → Critical
    
- 5–7 → High
    
- 3–4 → Medium
    
- <3 → Low
    

Это выглядит очень продвинуто на защите.

# 🔬 Дополнительные эвристики

### 📌 Фильтрация false positives

1. Если строка:
    
    - в тестах
        
    - в документации
        
    - содержит `example`
        
    - содержит `xxxx`
        
    - повторяющиеся символы
        

→ понизить вес.

---

### 📌 Игнорирование хэшей

Например:

- SHA256
    
- MD5
    

Они тоже выглядят случайными, но это не секреты.

Можно проверять:

- только hex?
    
- длина 32/64?  
    → возможно это хэш, понижаем приоритет.

# 🔎 Продвинутая идея (если хочешь выделиться)

### Sliding window анализ

Если строка длинная (100 символов), можно:

- разбивать на куски
    
- считать entropy каждого фрагмента
    
- искать “острова случайности”

# 🧠 Что такое semi-SAST простыми словами

Это когда ты:

> Не просто ищешь секрет в тексте,  
> а проверяешь — используется ли он где-то опасно.

То есть инструмент думает чуть глубже.

---

# 📌 Обычный поиск (regex)

Он делает так:

> О, вижу строку похожую на API-ключ → предупреждение.

Но он не понимает:

- используется ли этот ключ
    
- передаётся ли он в интернет
    
- это тест или реальный код
    

Он просто “ищет текст”.

---

# 🧠 Semi-SAST делает вот что

Он спрашивает:

1. Есть ли в коде секрет?
    
2. Куда он дальше идёт?
    
3. Попадает ли он в:
    
    - запрос в интернет?
        
    - логирование?
        
    - файл?
        

Если да → это реальная проблема.

---

# 🔎 Пример

### Код:

```python
API_KEY = "abc123"

requests.post(url, headers={"Authorization": API_KEY})
```

## Что делает умный анализатор:

1. Видит `"abc123"` → похоже на секрет
    
2. Помечает `API_KEY` как “опасная переменная”
    
3. Видит, что она передаётся в `requests.post`
    
4. Делает вывод:
    

> Хардкод ключа используется в сетевом запросе → 🔴 критично

---

# 🔁 Как он это понимает?

Очень просто:

Он запоминает:

```
API_KEY = секрет
```

Потом если видит:

```
что-то = API_KEY
```

Он тоже помечает это как секрет.

И если потом это попадает в опасную функцию — бьёт тревогу.

---

# 📦 Почему это называется semi?

Потому что:

Он:

- анализирует код
    
- понимает переменные
    
- отслеживает “куда что передаётся”
    

Но он:

- не супер сложный
    
- не строит сложные графы
    
- не анализирует 100 файлов глубоко
    

Это упрощённая версия профессионального анализатора.

---

# 🎯 В чём главная идея

Вместо:

> “Я нашёл строку”

Ты говоришь:

> “Я нашёл секрет и доказал, что он реально используется небезопасно”

Это огромная разница.

---

# ⚖️ Разница в одном предложении

**Regex** → ищет подозрительные строки.  
**Semi-SAST** → отслеживает путь секрета по коду.
